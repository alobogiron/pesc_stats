Defeitos encontrados

Os três surgiram de casos que ninguém escreveria testando o caminho feliz. Todos foram corrigidos e cada um ganhou um caso que trava a regressão.

1 · Uma célula malformada aborta o reprocessamento inteiro

Severidade alta dedup_publicacoes.py Corrigido
Sintoma

normalizar_doi([]) e normalizar_titulo_dedup([]) levantavam ValueError. A causa é que pd.isna devolve um array quando recebe algo array-like, e usá-lo num if é ambíguo.

ValueError: The truth value of an empty array is ambiguous.
Por que importa

O campo doi das três fontes é texto livre vindo de JSON e de API. Basta uma célula chegar como lista — um registro com dois identificadores externos — para o .map(normalizar_doi) estourar e derrubar o notebook inteiro. Falha total a partir de um dado ruim, sem degradação.

Correção

Helper _e_nulo() que trata a exceção e devolve False: o valor deixa de ser tratado como nulo e segue para a validação de formato, que o recusa. É o mesmo padrão defensivo que app.py já usava nos formatadores.

Trava de regressão

Caso A/1 passa 15 tipos diferentes (None, NaN, bytes, list, dict, tuple, numéricos) por ambas as funções.

2 · Upload sobrescreve uma base existente em silêncio

Severidade alta app.py · jobs.py Corrigido
Sintoma

O nome da base vem do nome do arquivo enviado, normalizado. Arquivos diferentes colidem no mesmo slug — CEFET/RJ.list e cefet rj.list viram ambos cefet_rj. O uploader gravava por cima sem qualquer aviso.

Por que importa

Só a lista era trocada. O .duckdb e os snapshots já extraídos continuavam descrevendo as pessoas da lista anterior. A base passava a mentir sobre si mesma — nome e conteúdo divergentes — até alguém reextrair, sem nada na tela indicando isso.

Correção

A decisão saiu da UI para jobs.salvar_lista_comparacao(), onde é testável: recusa por padrão, exige sobrescrever=True, e recusa sempre que houver job em andamento. A tela avisa que o banco não é atualizado e pede confirmação explícita.

3 · Nome longo vaza OSError e pode partir a base em duas

Severidade alta jobs.py Corrigido
Sintoma

Renomear para um nome de 300 caracteres estourava OSError: [Errno 36] File name too long. A UI captura apenas ValueError, então o erro subia como traceback na tela.

O risco pior, embaixo

A renomeação move os dez artefatos um a um. Com um nome no limite exato, os primeiros arquivos caberiam e os últimos não — o banco chama-se pesquisadores_comparacao_<nome>.duckdb, 25 caracteres a mais que a lista. A base ficaria partida entre dois nomes, metade sob cada um, sem nada que a reconciliasse.

Correção

_validar_nome_comparacao() confere o comprimento antes de mover qualquer arquivo e recusa como ValueError. Limite de 120 caracteres, com folga sobre os 33 que o artefato de nome mais longo acrescenta.

Trava de regressão

Um caso confirma a recusa em três tamanhos; outro, marcado como crítico, fotografa os dez artefatos antes e depois de uma recusa e exige que nenhum tenha se movido.

Um alarme falso que virou confirmação

Um caso acusou o sumiço da base cefet_list. A investigação mostrou que ela havia sido renomeada para cefet — pelo próprio commit fac0802, que o git registra como rename: 

scriptlattes/exemplo/comparacao/{cefet_list.list => cefet.list}
...duckdb => pesquisadores_comparacao_cefet.duckdb

Ou seja: a funcionalidade de renomear foi usada em produção e moveu todos os artefatos de forma consistente. O defeito era do teste, que trazia o nome fixo no código. Reescrito para fotografar as bases pré-existentes, quaisquer que sejam, e conferir que seguem intactas ao final.

Método

O que cada suíte procura

  • A — funções puras sob entrada que nenhum usuário digitaria: tipos errados, strings de centenas de quilobytes, DataFrames degenerados. Casos de desempenho usam alarme por sinal, para caçar explosão combinatória em vez de esperar indefinidamente.
  • B — o sistema de arquivos como adversário: path traversal, symlinks pendurados apontando para fora, diretório onde deveria haver arquivo, nomes no limite do NAME_MAX. Roda inteira em sandbox temporário.
  • C — as 11 páginas contra bases vazias, corrompidas e de outra arquitetura. Bancos derivados do real, em /tmp.
  • D — propriedades que o resultado tem de satisfazer, verificadas contra o banco de verdade. Não simula: audita o que o pipeline produziu.
  • E — o fluxo da interface, clicando nos widgets reais via AppTest. Única suíte que escreve no projeto; usa base descartável com prefixo zz_ e confere as pré-existentes ao final, sem nome fixo no código.

Como rodar

python testes_robustez.py              # todas as suítes
python testes_robustez.py A B          # só as escolhidas

# banco de referência para C e D (padrão: pesquisadores_teste.duckdb)
PESC_DUCKDB_REFERENCIA=/caminho/base.duckdb python testes_robustez.py

O que esta suíte não cobre

Registrado porque um relatório que só lista sucessos não ajuda ninguém a decidir onde olhar depois.

  • Concorrência real. Os lockfiles são testados por presença, não por corrida. Existe uma janela entre a checagem e o movimento dos arquivos (TOCTOU) que só apareceria com dois processos disputando a mesma base.
  • Rede. ORCID, Scopus e o scraping da Lattes não são exercitados. Timeout, resposta parcial e bloqueio por rate-limit ficam fora.
  • Volume. A base tem 31 docentes e 5.212 publicações. As medições de desempenho usam dados sintéticos maiores, mas nada foi rodado contra uma população de centenas de docentes.
  • O caso do nome no limite exato. A renomeação parcial hoje é impedida pela validação prévia, não por transação. Se um artefato futuro tiver nome mais longo que os atuais, o limite precisa ser revisto junto.
  • Navegador. AppTest executa o script do Streamlit, não renderiza. Layout, foco de teclado e comportamento em telas estreitas não são verificados aqui.
